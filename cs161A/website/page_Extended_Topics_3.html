File I/O: Reading and Writing Files

So far, most of our programs have had the memory span of a goldfish. You run them, type some input, get an answer, and then the whole little universe disappears the moment the program ends.

Files are how programs stop being so forgetful.

They let your program save data to disk, read data back later, and pass information around between different runs or even different programs. High scores? Files. Grade reports? Files. Logs? Files. Anything where "I really do not want to type all of this again tomorrow"? Also files.

The nice part is that file I/O is much less exotic than it sounds. If cin and cout already make sense to you, then the basic flow here will feel familiar too — in fact, the headline trick of this chapter is that the exact same >> and << operators you've been using to talk to the terminal also work on files, with almost no code change. The objects you connect them to are different, but the grammar of reading and writing is the same. That reuse is not an accident; it is one of the nicer things C++'s standard library does.

Variations on the theme: word by word, and "are we there yet?"

The first-file example grabbed one line at a time with getline. That's the right default when the file is naturally organized into lines — poems, configuration files, log files, grade reports, and so on. But sometimes a file is organized into words or numbers separated by whitespace, and you want a loop that hands you one token at a time without worrying about where the line breaks fall. If the file is exhausted, or the next chunk of the file can't be turned into a string, the read comes back as a failed state, the while sees "false," and the loop ends cleanly. Second, look at how little of the program is actually about words. The includes, the open, the error check, and the close are all doing the same job as the getline version. The only line that really changed is the one choosing how to read. That's the shape to expect: the surrounding bookkeeping is boring, and the interesting decision is "what shape of chunk do I want to pull off each iteration."

If that rhythm is starting to feel repetitive, excellent. File I/O is one of the places where boring habits are exactly what you want:

  1. connect a stream to a file
  2. check that the connection worked
  3. pick a reading pattern (getline for whole lines, inFile >> word for whitespace-separated chunks, inFile >> num for numbers)
  4. let the stream's own failure state end the loop when the file runs out
  5. close the stream when you're done

One small style note about the error check. You'll see both inFile.is_open() and inFile.fail() used for roughly the same purpose; the difference is mostly taste. is_open() is asking "did the file actually get connected?" while fail() is asking "is this stream currently in a broken state?" For the case where you just opened the file and want to know whether the open worked, they give you the same answer.

Writing to files, and the one new wrinkle

Reading files is half the story. The other half is producing them, and once you've seen the input version, the output version should feel almost embarrassingly familiar.

The shape is identical: make a stream, check that it opened, send stuff into it, close it. The only interesting swap is ifstream becoming ofstream, and getline becoming the familiar << operator — the exact same operator cout uses. You already know how to use <<. The only thing that changes is where the output lands.

A tab character \t shows up in the last three lines to line the columns up a little. You can write plain text, numbers, tabs, newlines — anything you'd be comfortable writing to cout works the same way here, and the result ends up inside output.txt on disk instead of on the screen.

One subtlety is worth pausing on. ofstream outFile("output.txt"); will happily create output.txt if it doesn't exist, and — here is the part that sometimes bites people — it will also obliterate any existing output.txt and start over. In other words, the default is "overwrite." That behavior is exactly what you want for something like a report that should be rewritten every run. It is very much not what you want for something like a running log, where every run should add to the end. For that, you need the next wrinkle.

Append Mode vs Overwrite Mode

Plain ofstream outFile("file.txt"); starts from scratch. If file.txt already exists, the new program run wipes it out and starts over.

ofstream outFile("file.txt", ios::app); says "no, no, keep what's already there and add the new stuff to the end." That is exactly what you want for logs, journals, and other running histories.

Processing CSV Files

CSV sounds fancier than it is. The basic move is:

  • get one whole record as a line of text
  • make a stringstream from that line
  • pull out comma-separated fields one by one
  • convert the fields that represent numbers

This is another clean split of responsibilities. The file stream worries about "which line are we on?" The stringstream worries about "which field are we on inside this line?"

A few useful ways to fail

The happy path for file I/O is short: open, read or write, close. Most of the "error handling" code you will ever write for files boils down to noticing which unhappy path you're on and saying something sensible about it.

There are three different "something went wrong" checks in that program and they are not the same check.

!inFile.is_open() catches the boring case: the file didn't open at all. Typo in the filename, wrong folder, file doesn't exist, you don't have permission, the disk is mounted read-only. These are the failures you get before you've read a single byte, and they almost always deserve a clean early exit.

inFile.bad() catches the scarier case: the file was fine when you opened it, but something went wrong while you were reading it. Think "disk got unplugged halfway through" or "the file was being deleted by another program while you were reading it." These are rare in student programs but worth checking in anything long-running.

inFile.fail() && !inFile.eof() catches the interesting case: the file existed, you could read from it, but somewhere in the middle the stream tried to read an int and found "banana" instead. The !inFile.eof() part matters because hitting the end of the file also puts the stream into a fail state, and that isn't actually an error — it's how while(inFile >> value) knew to stop in the first place. You only want to complain if the read stopped for a reason other than running out of file.

For most beginner programs, the is_open() check at the top is honestly all you need, and the other two checks are things you add if you're writing code that has to survive weird inputs.
