Common Algorithms & Problem Solving

Sooner or later every programmer gets tired of re-solving the same little problems from scratch.

How do I find something in a list?

How do I put a list in order?

How do I walk through some text looking for a pattern?

Those jobs come up so often that computer science has standard methods for them. Those standard methods are algorithms.

There is nothing mystical hiding in that word. An algorithm is just a step-by-step recipe for solving a recurring problem. The reason we care about them is that once you know a few solid recipes, whole categories of programming problems stop feeling like improvisation.

In CS161B you will study these ideas more formally, especially questions like "how fast is this?" and "when is this algorithm a bad choice?" For now I mostly want you to get comfortable tracing the logic and seeing the shape of the method.

Searching Algorithms

Linear Search

This is the simplest search algorithm: just look through an array one element at a time until you find what you're looking for (or reach the end without finding it).

You have actually already seen linear search in disguise. Binary Search (On Sorted Data)

Much faster than linear search, but only works on sorted arrays.

The variables left and right mark the current search window. At the beginning, that window is the whole array.

Each trip through the loop:

  1. compute the middle index
  2. compare the middle value to the target
  3. keep only the half where the target could still possibly live

That repeated halving is the whole reason binary search is so much faster than linear search on large sorted data.

The whole trick of binary search is that it throws away half the remaining search space each time. But it can only do that because the data is sorted. If the array is not sorted, then "go left" and "go right" stop meaning anything useful.

Time complexity: O(log n) - much faster for large arrays

Sorting Algorithms

Selection Sort

Find the minimum element and move it to the front, repeat for the rest.

Here's a complete demo:

Selection sort is a good first sorting algorithm because the idea is so direct: find the smallest remaining element and move it to where it belongs.

Try tracing that on paper with a tiny list like 8 3 5 1.

On the first pass, the algorithm finds 1 and swaps it into the first slot.

On the second pass, it ignores that first slot because it is already correct, then finds the smallest remaining value and puts that into the second slot.

So the sorted region grows from left to right one position at a time.

Bubble Sort

Repeatedly swap adjacent elements if they're in the wrong order.

Bubble sort is mainly useful for training your algorithm muscles because the movement is so local and visible: compare neighbors, swap if needed, repeat until the mess gradually untangles itself.

Problem-solving, when the problem stops being a one-liner

Once programs get past about fifty lines, a lot of the difficulty stops being "which C++ feature do I use here" and becomes something older and uglier: "what am I even trying to build?" This is the part of programming that doesn't show up in the syntax chapters, but it is where most of the real work hides, so it's worth naming out loud.

The shape of a successful beginner program, roughly, is this. First, you sit with the problem before you touch the keyboard. You read the prompt twice, identify what the program actually needs to take in and what it needs to produce, and write down at least one example by hand — input and expected output — so that "it works" is a question you can answer. Then you break the task into smaller pieces that each feel like things you know how to do. Then, and only then, do you start writing code, function by function, testing each small piece before you move to the next one. And when you're done, you go back and read what you wrote like a stranger would, and you usually find a way to make it shorter and clearer.

The single fastest way to get stuck is to skip the sitting-and-thinking step and leap straight from "I sort of understand the assignment" into typing. It feels productive because code is appearing, but the problem you're solving is still the vague one from your first reading, and you end up having to rewrite large chunks of the program once you notice what it was really asking for. Naming the inputs, outputs, edge cases, and subproblems on paper first almost always makes the coding part calmer.

Debugging on purpose

Debugging is a specific skill with its own rhythm, and the biggest difference between someone who's good at it and someone who isn't is almost entirely about how they spend the first five minutes when a program is broken.

The first thing to do when something goes wrong is to read the error message. This sounds obvious; it is not. Compiler errors, especially in C++, can be intimidating-looking walls of text, but the first line is almost always telling you exactly where the problem is and very close to what is wrong. Start there. If it isn't a compiler error, it's a runtime mistake, and then the job is to find out what the program was doing when it broke.

The cheapest debugging tool you will ever have is the cout statement. Printing out the values of variables at suspicious points in your program is not glamorous, but it works embarrassingly well because it replaces guessing with actually looking. "The loop condition looks right, I think" is an opinion; cout << "i " << i << endl;= is a fact.

From there, the other moves are basically about shrinking the problem until it fits in your head. If you suspect a specific function is wrong, call it from a tiny test program with inputs you know the answers to. If you suspect your input parsing is wrong, print the parsed values and stare at them before the interesting code ever runs. If you are deep in a weird bug and don't even know where to start, explain the code line by line to someone — or, if no one is around, to an inanimate object (the classic choice is a rubber duck). An absurd number of bugs are found halfway through describing the code, because the act of explaining forces you to notice the line where your mental model and the actual code disagree.

The thing to avoid, which is easy to fall into, is random thrashing: change a line, rebuild, change another line, rebuild, mutter, repeat. That feels productive because code keeps changing, but it rarely teaches you anything about what is actually wrong. The rule of thumb is "one change, one question, one new fact." If a change doesn't tell you anything new about why the program is misbehaving, the change wasn't actually helping.

Command-Line Arguments

Remember, back in the very first chapter --- when we were still echoing text back at ourselves --- when I joked that "we're very good programmers and never forget to put return 0 in our files"? I promised back then that we'd earn that joke eventually. This is the chapter where the joke stops being a joke.

Up to this point, return 0 has been a line you wrote because I told you to, and nothing in your programs has ever really cared what number you put there. When you run a program from the terminal, though, that number is not thrown away. The shell picks it up, and scripts and tools downstream watch for it to decide whether your program succeeded or failed. By convention, 0 means "I ran to completion and nothing went wrong" and any non-zero value means "something went wrong." That's why, in a few of the file I/O examples a while back, you saw return 1 used as the unhappy path — the program was signalling that this specific run did not succeed, even though the program itself compiled and launched just fine.

So the small polite ritual of ending main with return 0 was an innocent lie for the same reason the int-is-whole-numbers framing was: it was fine as long as your programs lived inside their own little sandbox, and it stops being fine the moment other programs start reading it. Command-line arguments are the first place it really matters, because programs that take arguments are usually programs that also get used by other programs, and those other programs absolutely check your exit code.

argc and argv

Programs can accept arguments from the command line.

Running: ./program hello world would output:

Number of arguments: 3
Argument 0: ./program
Argument 1: hello
Argument 2: world

Notice that all of these arguments arrive as text. Even if the user typed numbers, the program first receives them as strings and then decides whether to convert them.

argv[0] is usually the program name, so the user-supplied arguments begin at argv[1].
