Vectors: Dynamic Arrays

Remember all the little annoyances of arrays? Fixed size. Separate size bookkeeping. Passing the array and the length around together every single time. Out-of-bounds mistakes turning into chaos with no useful signal.

That whole list of annoyances is exactly why vectors exist. They handle most of the problems beginners keep slamming into with built-in arrays.

You'll use vectors constantly. They give you a container that tracks its own size, grows when you need more room, and works much more smoothly with functions. They are one of the first places where C++ starts feeling like it has decent tools built in.

Third, numbers.size() asks the vector how many elements it currently has. With basic arrays, keeping track of that count was our job. With vectors, the container keeps track of its own size for us.

The range-based loop at the end

means "for each number currently stored in the vector, bind it to num and run the loop body." That's a very natural fit for vectors because vectors are built to be traversed this way.

Making and filling vectors

The little program above already covered the "make an empty one, stuff things into it with push_back, ask it how big it is" motion, which is the whole core of how you use vectors day-to-day. But there's a handful of variations on making a vector that are worth knowing so that you recognize them when you see them in other people's code.

Here's one little program that shows four reasonable ways to conjure a vector into existence.

Nothing in this program is a new idea, but reading it lets you see all four styles side by side.

vector<int> numbers; is the "I don't know yet how many I need, I'll push_back them as they come in" style, which is what our first example used.

vector<int> grades(5); is "I know I need five, and I'd like them all pre-filled with zeros." You reach for that when you're about to use index-based access to overwrite those slots anyway, or when zero happens to be the right starting value (like a bunch of counters).

vector<int> temps {65, 68, 72, 75, 73};= is how you spell "here are the exact values I want right now." This is how quick test data gets written in real code.

And vector<string> names shows that this all works for any element type, not just int. The thing between the angle brackets is the type of one element; the vector is a container of those.

One footnote before we move on: a vector collecting things from user input is exactly the shape of program I kept wanting to write back in the arrays chapter, where we had to pick a size up front and pray. The sentinel tricks we pulled with bare arrays — -1 to mark the end, a separate numPets constant, dynLength walking the array until it hit a sentinel — are all things the vector just handles for you. That's the specific pain vectors were invented to take away.

What a vector knows about itself

Once you have a vector, there are a small number of questions you can ask it and a small number of things you can ask it to do. These methods come up constantly, so it's worth seeing them in one compact place.

Working through that program in order: push_back glues a value onto the end, pop_back removes the last one, size() reports how many are currently in there, empty() is a quick yes/no version of the same question, clear() throws everything away, and resize() forces the vector to have a specific number of elements (filling in default values if it has to grow, dropping elements off the end if it has to shrink).

You do not need to memorize all of this at once. The two methods you will reach for most often by an embarrassing margin are push_back and size(), with empty() and at() (which we're about to meet) as useful supporting actors. Everything else tends to show up when you need it, and you look it up.

Two ways to ask for an element, and why one of them is safer

The two ways you can pull an element out of a vector look almost identical until something goes wrong, so let's look at them together.

When the index really is in bounds, the two expressions give you the same thing. The difference only shows up when you ask for something that isn't there.

nums[0] is the old-school array-style access we saw back in the pointers chapter: it trusts you completely. If you ask for nums[10] on a five-element vector, you get the exact same kind of "off the edge of the world" misbehavior as plain arrays — silent, unpredictable, and very good at hiding bugs until two weeks later.

nums.at(0) asks the vector to check the index first. If you're in bounds, it hands you the element; if you're out of bounds, the program stops with a clear complaint about which index you tried and how big the vector actually is. That is much kinder to future-you at 2am.

This is exactly the kind of safety net the old arrays-and-sentinels chapter couldn't give you, and it is worth leaning on .at() for anything where you aren't absolutely certain the index is valid.

Walking through every element

The same "print all five values" task can be written two different ways, and both are common enough to recognize on sight.

The index-based loop is the right tool when the position is the thing you care about. If you want to print "item 3 is 15," or compare numbers[i] to numbers[i+1], or write to exactly one slot, you want i in your hands.

The range-based loop for(int num : numbers) is the right tool when you just want to visit every element and the index is clutter. You will read and write code like this constantly once you trust it, because "for each number in numbers" is genuinely what you meant to say.

The int& val variation is a small but important twist. Without the &, val is a copy of the stored value, and writing to val does nothing to the vector. With the &, val is the element — same box, not a new one — so assignments go through to the original vector. If you remember passing variables by reference back in the functions chapter, this is the same idea at loop scope.

Vectors passed into and returned from functions

Here is where vectors really start to pay rent, because they fix some of the most annoying things about passing arrays into functions. Remember, with bare arrays, every function that wanted to do something with the data also had to be told the length separately, because "an array" was really "a pointer and a promise about how far you could walk." With vectors, the container already knows its own size, and you can hand the whole thing to a function or get it back from one without any of the bookkeeping.

Let's look at three small functions that show the three patterns you'll reach for most often.

The three function signatures are doing three different jobs, and the difference between them is almost entirely in the type of the parameter.

const vector<int>& v means "give me the actual vector, not a copy, but I am promising not to change it." That is the sensible default for anything that only reads the data, because copying a huge vector just to peek at it is a waste. The const is what lets a future reader — and the compiler — know the function is a spectator.

vector<int>& v drops the const, and now the function is invited to modify the caller's vector in place. That's the whole point of doubleValues: it reaches in, multiplies every element by two, and when the function returns the caller's vector is different. Compare that to the bad old days of "also please pass me the length" and it should feel much cleaner.

vector<int> generateSequence(int n) returns a whole vector by value. For built-in arrays that would have been a nightmare — you can't really hand back an array from a function, so you had to do strange pointer tricks or require the caller to pre-allocate one. For vectors, it Just Works: generateSequence builds a local vector, returns it, and the caller gets a real vector back, size and all. Modern C++ quietly makes this cheap, so you are not paying for a giant copy every time.

Two-Dimensional Vectors

Once you accept the idea that a vector can hold anything of a given type, the next step is natural: a vector can hold other vectors.

The indexing works exactly the way you'd hope:

First choose a row, which gives you a vector. Then choose a column inside that row.

This is also why 2D vectors can be jagged: different rows are allowed to have different lengths, because each row is really its own vector.
