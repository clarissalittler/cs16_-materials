Structs: Organizing Related Data

Remember the little pet database from the arrays chapter, where we had two separate arrays — one for petNames, one for petSpecies — and a rule we had to enforce ourselves that petNames[i] and petSpecies[i] were always "the same pet"? That trick works for toy programs, but as soon as you need a third or fourth piece of information about each pet, it starts to feel rickety. Imagine doing the same thing for a student records program. You'd end up with something like:

And now you have a nightmare. To add a new student, you have to remember to push onto all four vectors, in the right order, with no typos. To delete a student, you have to delete from all four at the same index. If you ever accidentally add to three of them and not the fourth, the next student's name lines up with the wrong ID, and every student after that one quietly goes wrong. This is the same "keep it synchronized by hand, and hope" problem we had with the pet database, just scaled up to hurt more.

Structs solve this problem by letting you bundle related data together into a single custom type. Instead of four separate vectors, you can have one vector of "Student" objects, where each student carries all their own information. It's cleaner, safer, and much more intuitive.

Oh, and one bookkeeping note: see the }; at the end of the struct definition? Way back at the start of this book I told you that lines ending in { or } don't need semicolons, "with one annoying exception we'll get to." This is it. A struct definition is secretly a statement (it declares a type), so its closing brace needs the semicolon that every statement gets. Forget it and the compiler will produce some truly baffling error messages pointing at whatever innocent line comes next.

Another way to build a struct, and the "fill in the fields in order" shortcut

There are two styles for filling in a struct once you've declared one, and you will see both in real code, so it's worth showing them side by side.

The first style is the one we already met. Declare the variable, use the dot operator, assign one field at a time. It's verbose but very clear, and it's almost always the right choice when the field values aren't all available in the same place at the same time.

The second style,

is a compact way to fill in every field at once. The values show up in the same order the fields were declared in the struct, which is what makes this shortcut work at all. That's convenient, but also a small footgun: if you ever rearrange the fields in the struct declaration, every place in your code that used this shortcut quietly starts putting the wrong value in the wrong field, and the compiler will only complain if the types don't match up. For small programs it's fine; for bigger ones I tend to trust the dot-by-dot version.

You've already seen the dot operator a couple of times now, but just to say it once explicitly: myBook.title means "go into myBook, find the field called title, and hand me that." It is the same dot you'd use for reading or writing, so myBook.pages 400; changes the pages field and cout << myBook.pages;= prints it.

Structs flow through functions just like any other type

Once you've defined a struct, it is a real C++ type in every sense — which means it can be passed into functions, returned from functions, and stored in containers, the same way int or string can. That turns out to be one of the best reasons to use structs in the first place: they let you pass a record around your program as a single thing instead of juggling four or five separate variables.

Here's a small example that covers the two most common ways to pass a struct.

calculateArea(Rectangle rect) takes its parameter by value, which means the function gets its own private copy of the struct. For a Rectangle with two doubles in it, that copy is cheap and perfectly fine. For a big struct — one that holds, say, a string and a vector — copying it every time you passed it to a function would start to add up.

displayRectangle(const Rectangle& rect) uses the same "const reference" pattern we met with vectors: the & means "reach back into the caller's struct rather than making a copy," and the const is a promise to the reader (and to the compiler) that the function won't change it. This is a sensible default once structs start carrying enough data that copying is worth avoiding.

Returning structs: many answers from one function

Returning a struct may feel fancy at first, but the idea is actually straightforward: build one value that contains several related fields, then hand that value back to the caller. This is one of the cleanest ways to return "more than one piece of information" without juggling lots of separate variables.
