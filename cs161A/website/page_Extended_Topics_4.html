Multi-File Programs

Up to this point we have been cheerfully stuffing almost everything into one file, and for beginner programs that is honestly fine. But eventually one giant main.cpp stops feeling simple and starts feeling like you keep your entire life in one junk drawer.1

Need one function from line 1700? Good luck. Want to reuse your grade-calculation code in another project? Hope you enjoy copy-pasting. Found a bug in the reused code after you pasted it into three places? Outstanding. Now you get to fix it three times and wonder whether you missed one.

Also, while we're here: way back at the very beginning of this book, we treated #include <iostream> as basically a magic spell that let us say cout and cin. This is the chapter where the curtain goes up on what #include actually does. The one-sentence version is that #include is the compiler copying another file's contents into yours before compilation starts, and once you've seen that, the whole mental model of multi-file programs clicks into place.

You build this by asking the compiler to work with both .cpp files:

g++ -std=c++17 -Wall -Wextra main.cpp math_utils.cpp -o program

If that command works, you get a single executable program that behaves exactly like our one-file programs always have. The difference is that the source code is now split across three cooperating files.

Why three files, and why in this specific shape

Here is the idea the whole rest of this chapter depends on: the header file says what exists, and the implementation file says how it works.

Look again at math_utils.h. It doesn't contain any actual math. It just lists three function signatures — three names with their parameter and return types. It is a menu, not a kitchen. Any file that wants to use those functions gets handed the menu by saying #include "math_utils.h" and is now allowed to call them.

Then look at math_utils.cpp. This is the kitchen. It contains the actual function bodies, which is where the computation lives. It also starts by including its own header, which might look redundant but isn't — it lets the compiler double-check that the signatures in the kitchen match the signatures on the menu.

Finally, main.cpp includes <iostream> (for cout) and math_utils.h (for the math functions). Note the two different styles of #include: the angle brackets around <iostream> mean "look in the standard system locations," and the quotation marks around "math_utils.h" mean "look in my project folder first." So when we ask #include <iostream>, the compiler is quite literally pasting the contents of the standard iostream header into main.cpp before compiling, and that's how names like cout become visible. The "magic" we waved at in chapter one was this.

The reason to split a program up this way is that each piece can now be understood, tested, and reused on its own. If you wanted to write a second program that also needed factorial, you wouldn't copy the function's body; you'd just include math_utils.h and compile math_utils.cpp alongside your new main.cpp. No copy-pasting. One source of truth per function.

The weird lines at the top of the header

A few of the lines in math_utils.h are going to look a little alien, and they deserve their own little explanation.

That trio is called an include guard. It exists because, in a non-trivial program, it is very easy to end up with the same header being included more than once through different paths, and that causes the compiler to complain about seeing the same declarations twice. Read the guard literally and it almost explains itself: "if the name MATH_UTILS_H hasn't been defined yet, define it now, and then process everything up to #endif. If this header ever gets dragged in again later, the name is already defined, so the body gets skipped." It's an ugly-looking idiom but the idea is one sentence: include these declarations once, no matter how many places ask for them.

The reason the syntax looks strange is that these lines are not really C++ code; they are instructions to the preprocessor, which is a small tool that runs over your source before the actual C++ compiler sees it. The preprocessor is the thing doing the pasting when it sees #include, and it's the thing toggling the guard when it sees #ifndef. Once you know it's a separate, simpler tool with its own language, the funny hash marks stop feeling mysterious.

Two messages the linker loves to give you

Multi-file programs introduce a small family of error messages that beginners find disproportionately scary. They don't need to be.

The first is "multiple definition of foo." It means the linker — the tool that stitches the compiled pieces together at the end — found more than one implementation of the same function, and it has no idea which one you meant. Almost always, this happens because a function body accidentally wound up in a header file, and the header got included in two different .cpp files, so each one built a copy. The fix is to move the function body into an implementation file and leave only the signature in the header. Header files advertise; implementation files provide.

The second is "undefined reference to foo." This is the mirror image: the compiler saw a call to foo and a header saying foo was supposed to exist, but by the time the linker goes looking for the actual body, nothing has turned up. Almost always, this means you compiled main.cpp on its own and forgot to list math_utils.cpp on the build command, so the kitchen was never built. The fix is to make sure every implementation file the program needs is actually being compiled and linked in.

If you remember that headers promise functions exist and implementation files deliver on those promises, both errors start to read like the specific broken promises they are.
