Arrays, again, and Pointers

Remember, a few chapters ago, when I introduced arrays and warned you that the "fixed-size box you have to count yourself" framing was only half the story? This is where the other half shows up.

The short version of the reveal: a C/C++ array is not really a "box with slots" at all. It is more like an address in memory and a promise — a promise you, the programmer, are making — that there are so many valid things stored right after that address. The compiler does not check the promise. Stepping off the end does not feel like a wall because there is no wall; there is just the next address, which happened to belong to something else.

That is the half of the story we're about to unpack. To do it honestly, we first have to meet a new idea called a pointer, which is literally "a variable that stores an address." What's that, exactly? A number, and yes this is a number despite the letters mixed in there, that starts with 0x is a hexadecimal number. Remember how we talked about binary being a sum of powers of two and our normal base ten is a sum of powers of ten? Hexadecimal is powers of 16, where the "digits" used in a hex number range from 0-f rather than 0-9. Hex is a little weird to read but it's really convenient for talking about computers because each hex digit is the same as 4 bits of information.

Have you ever seen hex-codes for colors? They're usually a series of 6-hex digits because an rgb color is 24 bits, or 3 bytes, i.e. 6 groups of 4 bits each.

However, when you see a big hex number in programming it's usually a memory address. An address is what it sounds like, it tells you where the information is stored in the computer's memory, completely analogous to a street address.

Do you remember earlier in this text when we talked about the storage wall with the labeled dividers? Well these addresses are what those labels really are.

And this means that when you use the name of the array by itself, without the [], in a context like this, C++ converts it into the address of where the array starts. That's an important subtlety: an array is not literally the same thing as a pointer, but in many expressions it "decays" into a pointer to its first element.

Pointer and a promise

Okay, now the reveal I kept gesturing at. "The box with slots" was a useful fiction. What an array actually is, as a runtime thing, is an address — the place in memory where the first element lives — together with an unwritten promise from you that so many more elements of that type sit right after it. The name of the array, in most expressions, "decays" into exactly that address. The square brackets arr[i] are not asking a box for its i-th compartment; they are asking the compiler to start at the address, jump forward by i elements' worth of memory, and look at whatever is there.

That is genuinely the whole story, and it explains all the annoyances we flagged when you first met arrays:

  • you have to remember the size yourself, because a bare address has no size attached to it
  • passing an array to a function really means passing the address, which is why functions that take arrays have to agree on some other convention (a sentinel, or an explicit length parameter) to know when to stop --- we'll write a function called dynLength in the very next section that does exactly this
  • out-of-bounds access does not fail loudly, because there is nothing on the address line marking where your memory ends and someone else's begins; you just keep reading

So when I told you earlier that arrays were fixed-size boxes you had to count yourself, the fixed-size part was a kind-of lie and the "count yourself" part was the whole job, not an inconvenience. That's the reveal.

In modern programming, you don't use basic C/C++ style arrays that often. Even in C++ most of the time you're going to use a data structure we call a vector. These vectors are what most programming languages call arrays, like Python, and they're capable of doing things like

  • changing in size
  • adding and deleting elements
  • telling you how many elements are currently in them
  • let you ask for bounds-checked access with .at()

Very convenient!

We won't really use vectors in this class and that's because we're trying to install fear of healthy respect for the problems that can happen if you aren't careful using arrays.

How ints are actually stored, and why string::npos is 18446744073709551615

While we are being honest about what memory looks like, we can finally close another loop I left hanging. Way back when we first introduced int, I said "treat these as the whole numbers you already know, with a small warning that they aren't quite that." And a while after that, when we met find and string::npos, we saw that searching for something not in a string gave back a ridiculous answer like 18446744073709551615 and I asked you to just file it under "weird but consistent." This is where those two loose ends get tied together.

Here is the honest version. When C++ makes an int, it sets aside a fixed amount of space — on almost every machine you're likely to use, that's 32 bits, though other sizes exist. That means an int can only represent a fixed, finite range of whole numbers. It is not the integers from your math class; it is a finite window onto them. If you try to add two int s and the true result doesn't fit in that window, you've caused what's called "overflow," and it is the real reason I was cagey about whether int was really the whole numbers. What you'll usually observe when a plain int overflows is the stored answer wrapping around, the way a car odometer rolls over from its biggest reading back to zero --- but I have to be honest here too: for signed types like int, the C++ standard doesn't promise the wraparound. It calls overflowing an int undefined behavior, which means the compiler is allowed to assume it never happens. Only the unsigned types we're about to meet get the odometer roll guaranteed in writing.

Now the second loose end. There is a second variety of integer type in C++ called unsigned. Unsigned types are the same fixed width, but they do not spend any bits on representing negative numbers — they use the full range for zero and positive numbers. The function string::find returns one of these unsigned types, because an index into a string is never supposed to be negative.

Here comes the punchline to the -1 trick. Imagine a small odometer that can only show three digits, so the readings go 000 through 999. If you are sitting at 000 and you try to subtract one, the odometer wraps around and the next reading is 999, because there is literally nowhere else for the digits to go. A real unsigned integer in C++ works exactly the same way, just with a much bigger odometer. On a 64-bit machine the unsigned integer that find uses has its biggest reading at 18446744073709551615, and "one less than zero" wraps around to exactly that value. That is why -1 and string::npos end up comparing equal even though they look like wildly different numbers: the bit pattern you get by writing -1 and forcing it into an unsigned type is the same bit pattern as "the biggest unsigned value there is."

And the specific constant 18446744073709551615 is 2^64 - 1, which is just "the largest number you can spell with 64 binary digits when all of them are 1s." string::npos is defined to be that maximum value so that it will never collide with a legitimate index.1

So, to collect the promises I've been making:

  • int is a finite, fixed-width window onto the integers; that's why the "whole numbers you know" framing was only an innocent lie
  • overflow is what happens when a calculation tries to leave the window
  • string::npos is huge because it is deliberately chosen as the biggest possible unsigned value, so that it cannot be confused with any real position
  • -1 and string::npos compare equal because pushing -1 into the unsigned type wraps the odometer back to the top

With that cleared up, we can go back to writing if(str.find("test") string::npos) in good conscience and actually mean it when we say it.

Sentinel-terminated arrays

If we wanted to approximate arrays that were a little more flexible, without using the vector type or real dynamic allocation, what might we do?

One idea is that we could make an array that's a lot bigger than we really need and then only use part of it, marking the "effective" end with some kind of special piece of data.

Let's assume that the arrays we're going to make are going to be arrays of natural numbers, so 0 and above. That means we could treat -1 as the special "this is the end of the used portion" value. This -1 is called a sentinel.

This is not the same thing as a true dynamically sized array. The actual array size is still fixed. We're just storing an extra convention inside it.
